# Database Schema

The table-by-table reference for the PostgreSQL schema. It is generated by hand
from the SQLAlchemy models in `backend/app/models/`, which are the schema truth;
the initial Alembic revision
(`backend/alembic/versions/475444f9f837_initial_migration.py`) creates exactly
this shape. How changes reach a running database is in
[`migrations.md`](migrations.md).

---

## 1. Conventions

| Convention | Rule |
|------------|------|
| Primary keys | autoincrement integer `id` (except `invoice_counters`, `subscriptions`: `business_id` is the PK) |
| Tenancy | every tenant-owned table has `business_id` with an FK to `businesses.id` and a `CASCADE` delete |
| Timestamps | `created_at` with `server_default CURRENT_TIMESTAMP` |
| Soft delete | `is_active` boolean (categories, products, suppliers, customers, users); nothing is hard-deleted for business data |
| Money | `Float` columns rounded to 2 decimals by the routers; see the caveat in §4 |
| Enums | `app/models/enums.py`: `Role` (`Owner`/`Manager`/`Cashier`), `InventoryTxType` (`purchase`/`sale`/`return`/`adjustment`) — stored as strings |
| Ledger | `inventory_transactions` is append-only; a quantity is never corrected by editing a ledger row |

Cross-tenant access is prevented in the query layer (`ctx.business_id` filter),
not by database row-level security — see
[`../architecture/data-flow.md`](../architecture/data-flow.md).

## 3. Tables

### Identity and tenancy

| Table | Columns |
|-------|---------|
| `businesses` | `id` PK · `name` · `address` · `phone` · `email` · `logo_path` · `currency` · `tax_rate` · `invoice_format` · `min_stock_default` · `created_at` |
| `users` | `id` PK · `name` · `email` (unique) · `phone` (unique) · `hashed_password` (bcrypt) · `is_active` · `created_at` |
| `user_business` | `id` PK · `user_id` FK · `business_id` FK · `role` · `is_active`; unique `(user_id, business_id)` |
| `password_reset_tokens` | `id` PK · `user_id` FK · `token` (unique, opaque) · `expires_at` · `used` |
| `subscriptions` | `business_id` **PK** FK · `plan` · `status` · `product_limit` · `employee_limit` · `updated_at` |

`users.email` and `users.phone` are nullable but each is unique when present, so
a user may register with either. One login can hold several memberships with a
different role per business.

### Catalogue

| Table | Columns |
|-------|---------|
| `categories` | `id` PK · `business_id` FK · `name` · `description` · `is_active` · `created_at`; unique `(business_id, name)` |
| `products` | `id` PK · `business_id` FK · `category_id` FK (nullable) · `name` · `sku` · `barcode` · `brand` · `unit` · `purchase_price` · `selling_price` · `min_stock` · `quantity_on_hand` · `is_active` · `image_path` · `created_at` |

Unique constraints `(business_id, sku)` and `(business_id, barcode)` enforce the
FR-5.7 rule that duplicates are impossible **within a business** while the same
code may exist in another tenant. Product images are stored as a file path in
`products.image_path` (there is no `product_images` table) under `UPLOAD_DIR`.

### Parties

| Table | Columns |
|-------|---------|
| `suppliers` | `id` PK · `business_id` FK · `company_name` · `contact_person` · `phone` · `email` · `address` · `outstanding_balance` · `is_active` · `created_at` |
| `customers` | `id` PK · `business_id` FK · `name` · `phone` · `email` · `address` · `credit_limit` · `outstanding_balance` · `is_active` · `created_at` |

`outstanding_balance` is maintained by the trading write paths (credit sales,
supplier payments, cancellations) — it is derived data, not a source of truth.

### Inventory

| Table | Columns |
|-------|---------|
| `inventory_transactions` | `id` PK · `business_id` FK · `product_id` FK · `quantity_change` (signed) · `tx_type` · `reason` · `user_id` FK (nullable) · `related_id` (e.g. `sale:12`) · `created_at` |
| `price_adjustments` | `id` PK · `business_id` FK · `product_id` FK · `old_selling_price` · `new_selling_price` · `old_purchase_price` · `new_purchase_price` · `reason` · `user_id` FK · `created_at` |

The ledger is append-only and is the audit trail for every stock movement:
`sum(quantity_change)` for a product must equal
`quantity_on_hand - <opening quantity>`. `price_adjustments` keeps price history
that `products` alone would lose.

### Trading

| Table | Columns |
|-------|---------|
| `purchases` | `id` PK · `business_id` FK · `supplier_id` FK · `purchase_date` · `subtotal` · `discount_amount` · `tax_amount` · `total_amount` · `paid_amount` · `payment_status` · `status` · `note` · `created_by` FK · `created_at` |
| `purchase_items` | `id` PK · `purchase_id` FK · `product_id` FK · `quantity` · `unit_cost` · `line_total` |
| `sales` | `id` PK · `business_id` FK · `invoice_no` · `customer_id` FK (nullable) · `subtotal` · `discount_amount` · `tax_percent` · `tax_amount` · `total_amount` · `paid_amount` · `payment_method` · `payment_status` · `status` · `refunded_amount` · `sold_by` FK · `created_at`; unique `(business_id, invoice_no)` |
| `sale_items` | `id` PK · `sale_id` FK · `product_id` FK · `quantity` · `unit_price` · `discount` · `line_total` · `returned_qty` |
| `sale_returns` | `id` PK · `business_id` FK · `sale_id` FK · `reason` · `refund_amount` · `created_by` FK · `created_at` |
| `sale_return_items` | `id` PK · `return_id` FK · `sale_item_id` FK · `product_id` FK · `quantity` · `refund` |
| `invoice_counters` | `business_id` **PK** FK · `last_seq` — the per-business invoice sequence behind `Business.invoice_format` |

`payment_status` is one of `paid` / `partial` / `unpaid`; `status` is
`completed` / `cancelled` for sales and `received` / `cancelled` for purchases.
`returned_qty` on `sale_items` is what makes a partial refund idempotent: a
return can never exceed `quantity - returned_qty`.

### Finance and platform

| Table | Columns |
|-------|---------|
| `expenses` | `id` PK · `business_id` FK · `category` · `amount` · `description` · `expense_date` · `payment_method` · `created_by` FK · `created_at` |
| `audit_logs` | `id` PK · `business_id` FK · `user_id` FK (nullable) · `action` (e.g. `sale.checkout`) · `resource` · `resource_id` · `old_value` · `new_value` · `created_at` |
| `ai_recommendations` | `id` PK · `business_id` FK · `kind` · `title` · `body` · `reviewed` · `acted_upon` · `created_at` |

`audit_logs.old_value` / `new_value` are truncated at 2000 characters by
`services/audit.write_audit` to bound row size.

## 5. Caveats

- **Money is stored as float.** Arithmetic is rounded per operation
  (`round(..., 2)`) and covered by `tests/test_finance_reports.py`, but there is
  no decimal type — a future migration to `Numeric(12, 2)` is the correct fix
  for long-lived ledgers.
- **`quantity_on_hand` is a cached aggregate.** The ledger is authoritative;
  reconcile with `sum(inventory_transactions.quantity_change)`. See the known
  gap recorded in
  [`../architecture/data-flow.md`](../architecture/data-flow.md#2-stock-write-path-the-most-important-invariant).
- **No database-level row-level security.** Tenancy is a query-layer
  responsibility, so a hand-written query that forgets `business_id` would leak
  across tenants. Contract tests in `tests/test_employees_rbac.py` cover the
  isolation rule at the API level.
- **Dialect portability.** ORM queries avoid Postgres-only constructs so the
  suite can run on SQLite ([ADR 0002](../architecture/decisions/0002-postgres-primary-sqlite-for-tests.md));
  anything dialect-specific belongs in a migration, not in application code.
